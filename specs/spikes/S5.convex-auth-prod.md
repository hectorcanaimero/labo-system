# S5 · Convex Auth prod-ready vs Clerk

## Objetivo

Validar que **Convex Auth** (provider Password) cubre todos los requisitos v1 antes de escribir `F0.auth`. Si algún gap es bloqueante, activar Plan B (Clerk).

Auth es fundacional y migrar tarde es caro — este spike se resuelve en día 1 del proyecto.

## Contexto

- PRD §4 F9: password login, roles Admin/Operador, sesiones ~8h.
- ARCH ADR-03: Convex Auth nativo con Plan B Clerk.
- Requisitos ampliados no cubiertos explícitamente por Convex Auth out-of-the-box:
  - Recuperación de contraseña (email).
  - Invitación de usuarios nuevos por Admin.
  - Rate limiting en login.
  - Expiración/refresh de sesión.
  - Auditoría de accesos.

## Alcance

Sí hace:
- Instalar Convex Auth en un scratch project y validar:
  - Signup/signin password.
  - Sesión persistente vía cookie httpOnly.
  - Refresh automático.
  - `ctx.auth.getUserIdentity()` en queries/mutations.
- Prototipar (o al menos diseñar en detalle) los 5 gaps:
  1. Password reset (endpoint action + tabla `password_reset_tokens` + email).
  2. Invitación (Admin crea usuario, envía email con token, usuario elige password).
  3. Rate limit login (5 intentos / 15 min por email, tabla `login_attempts`).
  4. Sesión 8h (config Convex Auth + verificar refresh).
  5. Audit log de login/logout (`audit_log` con `accion: "auth.login"`).
- Estimar horas por cada gap y comparar contra costo de adoptar Clerk (mensual + integración).
- Decisión final documentada con criterio explícito.

No hace:
- Implementar el auth final (eso es F0.auth).
- Implementar email transaccional (Resend/otro) más allá de un stub para el POC.
