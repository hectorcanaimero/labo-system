# S2 · Migración WP → Convex

## Objetivo

Mapear al detalle las tablas custom del plugin `rv-laboratorio v1.2.1` (MySQL) a las colecciones Convex del ARCH, para que el script `F1.migracion.T*` pueda escribirse con contrato claro y ejecutarse idempotente (dry-run + real).

## Contexto

- PRD §10 (S2) y ARCH ADR-10 fijan estrategia: script Node standalone con `mysql2` (readonly) + `ConvexHttpClient` (deployKey) + tabla auxiliar `_migration_map`.
- Fuente: tablas `rv_pacientes`, `rv_titulos`, `rv_examenes`, `rv_paquetes`, `rv_resultados`, `rv_resultados_detalle`, `rv_presupuestos`, `rv_presupuestos_detalle` (nombres tentativos — validar contra dump real).
- Volumen origen: 204 pacientes, 250 exámenes en 6 grupos, 652 resultados, 545 presupuestos, 9 paquetes.
- Cédulas con formato inconsistente (`V-21197865`, `V- 33338896`, con puntos/espacios) — hay que normalizar y reportar conflictos.

## Alcance

Sí hace:
- Obtener dump MySQL de prod (o credenciales readonly).
- Enumerar TODAS las tablas custom del plugin y sus columnas/tipos.
- Mapear cada columna WP → campo Convex del schema (`packages/convex/schema.ts` — ver ARCH §6).
- Documentar el formato real de cédulas en dataset actual + regex de normalización.
- Documentar los 6 grupos actuales de exámenes con nombre y count (input a S4).
- Detectar duplicados existentes (nombres exactos, cédulas repetidas) con reporte.
- Definir estrategia de snapshot histórico (los detalles de resultados/presupuestos deben preservar el `nombre` y `precio` originales al momento).
- Prototipar un dry-run parcial (pacientes + 1 examen) que reporta N filas leídas, N a insertar, N conflictos.

No hace:
- Ejecutar migración real contra prod.
- Escribir el script final completo (eso es `F1.migracion.T*`).
- Cutover.

## Criterios de aceptación

- [ ] Documento con esquema real MySQL de cada tabla `rv_*` (columnas + tipos + FKs implícitos).
- [ ] Tabla de mapping WP → Convex fila a fila (`{ wp_table.column → convex_table.field, transform }`).
- [ ] Regex y función `normalizeCedula` validada contra el 100% del dataset actual + reporte de casos no matcheados.
- [ ] Lista de duplicados detectados (catálogo + cédulas) con propuesta de resolución.
- [ ] Snapshot strategy documentada: qué columnas WP → `nombre_snap` / `precio_snap` en `resultados_examenes` y `presupuestos_examenes`.
- [ ] POC de dry-run funcional que corre en < 1 min sobre subset.
- [ ] Lista definitiva de los 6 grupos (nombre + count exámenes) para input a S4.

## Notas técnicas

- IDs: Convex IDs son opaque strings, no int. El script genera IDs Convex nuevos y usa `_migration_map` (`{ wp_table, wp_id, convex_id, migrated_at }`) para trazabilidad + idempotencia.
- Convex `ConvexHttpClient` con `deployKey` (env var `CONVEX_DEPLOY_KEY_MIGRATION`).
- No usar Convex action (bundle enorme + límite 10min). Script standalone Node.
- `mysql2` es devDep del script, no del monorepo.
