### F0.2.T7 — Invitación de usuarios (Admin only)

- **Objetivo**

Admin puede invitar nuevos usuarios (Admin u Operador) por email con token; el invitado elige su password.

- **Contexto**

InsForge no tiene flujo de invitaciones: se mantiene el diseño custom de tokens, pero el alta del usuario se hace contra InsForge Auth (creación admin-side) y el email viaja por InsForge Messaging. La creación pública está deshabilitada; sólo por invitación.

- **Alcance**

Sí hace:
- Tabla `user_invitations` en `packages/db` (`email`, `role`, `token_hash`, `invited_by`, `expires_at`, `accepted`) — incluida en migración F0.1.T8.
- Route Handler `POST /api/usuarios/invite` (Admin only) → genera token → envía email vía InsForge Messaging SDK.
- Página `/accept-invite?token=...` con form (password + confirm).
- Route Handler `POST /api/usuarios/accept-invite`: valida token, crea usuario en InsForge Auth (admin create user o signup con verificación), inserta fila `usuarios` con `auth_user_id` y role, marca invite aceptado — todo en una transacción Postgres para la parte de dominio.
- UI mínima en `/config` (o `/usuarios`) con lista de pendientes + botón "Invitar".
- TTL invite: 7 días.

No hace:
- Gestión avanzada (revocar, re-invitar, cambiar rol post-alta) — se maneja desde el dashboard de InsForge v1 si es necesario.

- **Criterios de aceptación**
  - [ ] Admin puede invitar; Operador no ve el botón.
  - [ ] Email de invitación se envía (o loguea en dev).
  - [ ] Aceptar invite crea user con rol correcto y fila `usuarios` vinculada por `auth_user_id`.
  - [ ] Token expirado rechaza.

- **Notas técnicas**

Reusar helper de email de T06 (Messaging SDK). La UI de invitación puede vivir dentro de F1.config para no crear un módulo `/usuarios` separado en v1.
